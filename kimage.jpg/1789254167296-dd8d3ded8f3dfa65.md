# 什么是高质量 Skill：从 Prompt 到可持续能力系统

## 1. 核心定义

一个高质量的 **Skill**，本质上不是一段写得很长、要求很多的 Prompt，而是一套围绕明确任务目标构建的、可以被正确发现和触发、能够稳定执行、结果可以验证、过程能够追踪、版本可以持续迭代的能力系统。

可以将高质量 Skill 概括为六个关键词：

> **可发现、可决策、可执行、可验证、可治理、可进化。**

进一步可以写成：

> **Skill = Job Story + Routing + Decision Protocol + Workflow + Resources + Execution + Evaluation + Governance**

这比传统的：

> Role + Prompt + Output

更加完整。

---

# 2. 什么才算一个好的 Skill

一个高质量 Skill，至少应该同时满足以下几个维度。

| 维度 | 高质量表现 | 常见失败信号 |
|---|---|---|
| 目标聚焦 | 围绕一个明确 Job Story 展开 | 把多个不同任务塞进一个万能 Skill |
| 触发精准 | 该触发时触发，不该触发时不触发 | 只靠关键词匹配，误触发、漏触发严重 |
| 决策明确 | 能根据上下文、输入和条件选择不同策略 | 所有任务都走一条固定流程 |
| 流程闭环 | 包含解析、判断、执行、异常、验证和交付 | 只有几个理想步骤，没有失败分支 |
| 自由度适配 | 模型判断、规则约束、脚本执行合理分工 | 要么全部交给模型，要么全部写死 |
| 上下文经济 | 核心规则留在 SKILL.md，知识按需加载 | SKILL.md 变成百科全书 |
| 可验证 | 有明确 Definition of Done、Rubric 与检查项 | 用“专业”“高级”“看起来不错”作为标准 |
| 可治理 | 有版本、权限、数据边界、灰度、监控、回滚 | 在线直接改核心规则，无法解释变化 |
| 可迭代 | 真实失败可以沉淀为 Eval，并驱动最小改动 | 每次出问题都只是继续堆 Prompt |

因此，可以将一个好的 Skill 定义为：

> **围绕单一明确任务目标构建，能够被准确触发，根据输入自主决策，通过可靠流程完成任务，并使用明确标准验证结果，同时具备版本化和持续迭代能力的能力单元。**

---

# 3. 第一原则：从 Job Story 开始，而不是从目录开始

写 Skill 时，不应该首先思考：

> “这个 Skill 里面应该包含哪些功能？”

而应该先回答：

> **谁，在什么情况下，为了完成什么目标，需要这个 Skill 帮他得到什么结果？**

推荐统一使用以下 Job Story 结构：

```text
当【某类用户】
在【某种场景】
需要【完成某个任务】时，

这个 Skill 应该帮助他
获得【明确结果】，

并满足【成功标准】。
```

例如，一个九宫格分镜 Skill，可以定义为：

```text
当用户提供剧情、故事梗概或视频创意，
希望将其转化为可直接用于图像模型生成的连续九宫格分镜时，

本 Skill 将剧情拆解为 3×3 Storyboard，
并确保人物身份、空间关系、动作衔接和镜头节奏具有连续性，
最终输出可直接用于图像模型生成的高密度视觉提示词。
```

而不建议定义成：

```text
这是一个能够生成剧情、分镜、视频 Prompt、
图像 Prompt、镜头语言、风格设计的万能 Skill。
```

因为一个 Skill 解决的问题越多，路由、输出和质量标准就越难稳定。

---

# 4. Skill 的第一层不是 Workflow，而是 Discovery / Routing

Skill 写得再好，如果触发错了，后面的能力几乎没有意义。

因此，一个成熟 Skill 应该首先定义：

- **Positive Cases：应该触发**
- **Negative Cases：不应该触发**
- **Boundary Cases：边界场景，需要进一步判断**

## 4.1 Positive Cases

例如九宫格分镜 Skill 应该处理：

- 帮我把这个剧情拆成九宫格分镜
- 根据故事梗概生成连续 Storyboard
- 将 plot_summary 拆成 9 个连续画面
- 我要一组可以直接用于生图的分镜提示词

## 4.2 Negative Cases

不应该处理：

- 帮我写一个完整剧情
- 帮我剪辑视频
- 分析一下这张照片
- 帮我做一个海报
- 生成一条单镜头视频 Prompt

## 4.3 Boundary Cases

例如用户只说：

```text
帮我做一个 15 秒视频。
```

这时不应该直接触发九宫格 Storyboard Skill。

因为用户可能真正需要的是：

- 视频 Prompt
- 分镜脚本
- Storyboard
- 剧情设计
- 生图 Prompt
- 视频生成 Prompt

所以高质量 Skill 的目标不是单纯提高召回率，而是同时优化：

> **Precision + Recall**

即：

> 应该触发时能被找到，不应该触发时不要过度接管。

# 5. 好的 Skill 不是“步骤很多”，而是有 Decision Protocol

普通 Prompt 往往是：

```text
Step 1
Step 2
Step 3
Step 4
```

但真正成熟的 Skill，更接近：

```text
输入
↓
识别任务
↓
判断当前状态
↓
选择策略
↓
执行
↓
验证
↓
是否满足完成条件？
├─ Yes → 交付
└─ No  → 修正 / 降级 / 请求澄清 / 停止
```

也就是说：

> **Skill 的核心不是步骤，而是决策。**

每一个关键节点最好能够回答五个问题：

1. 需要什么输入？
2. 如何判断当前状态？
3. 下一步做什么？
4. 失败怎么办？
5. 什么时候停止？

例如：

```md
## 人物一致性判断

### 输入

需要读取：

- 当前角色身份信息
- 上一镜头角色状态
- 当前镜头剧情要求
- 用户明确的人物参考或约束

### 判断

如果剧情没有明确要求：

- 换装
- 时间跨越
- 身份变化
- 年龄变化
- 场景逻辑导致的造型变化

则人物核心视觉身份必须保持一致。

### 必须保持

- 年龄感
- 性别表现
- 发型
- 发色
- 面部核心特征
- 主体服装
- 身材比例
- 关键配饰

### 允许变化

- 表情
- 姿势
- 镜头角度
- 景别
- 动作状态
- 合理的环境光变化

### 失败处理

如果发现当前镜头与上一镜头发生无剧情依据的身份漂移：

1. 保留剧情动作；
2. 恢复上一镜头核心身份信息；
3. 重写当前镜头；
4. 再次执行一致性检查。

### 停止条件

人物身份、剧情状态与视觉连续性均满足要求后，进入下一阶段。
```

这已经不再只是 Prompt，而是一套：

> **Decision Protocol / 决策协议**

# 6. 为每一步分配合适的自由度

高质量 Skill 不应该把所有任务都交给大模型，也不应该把所有步骤都机械写死。

更合理的方式，是给不同任务分配不同自由度。

---

## 6.1 高自由度：交给模型判断

适合：

- 语义理解
- 创意判断
- 情绪理解
- 风格选择
- 构图选择
- 镜头语言
- 策略选择
- 信息优先级判断

例如：

```text
根据当前剧情重点选择最适合的景别。

如果剧情重点是人物情绪，
优先考虑中近景、近景或特写。

如果剧情重点是空间关系，
优先考虑全景、中远景或建立镜头。
```

不建议机械写死：

```text
第一镜必须全景。
第二镜必须中景。
第三镜必须特写。
```

除非这是业务硬要求。

---

## 6.2 中自由度：规则 + 参数 + 模型判断

适合：

- 镜头数量
- 节奏
- 结构
- 信息密度
- 风格变化范围
- 模板选择

例如：

```text
默认输出 9 个镜头。

如果剧情信息密度较低：
允许多个镜头承担情绪递进和空间建立。

如果剧情信息密度较高：
每个镜头优先只承担一个核心动作或剧情节点。

如果剧情包含明确高潮：
应为高潮保留至少一个高视觉权重镜头。
```

---

## 6.3 低自由度：脚本 / Schema / Tool

适合：

- 精确计算
- 格式转换
- JSON 校验
- 文件处理
- 批量重命名
- 去重
- 编号
- 尺寸换算
- 稳定的数据抽取
- 固定命令执行

原则是：

> **让模型负责判断，让规则负责约束，让脚本负责确定性。**

---

# 7. Skill 的六层架构

一个成熟 Skill 可以拆成六层。

---

## 7.1 发现层 Discovery

解决：

> **什么时候应该使用这个 Skill？**

主要包含：

- name
- description
- trigger intent
- positive cases
- negative cases
- boundary cases
- 可选界面元数据

发现层决定：

- Skill 是否能被找到
- 是否会误触发
- 是否会漏触发

---

## 7.2 编排层 Orchestration

解决：

> **任务应该如何完成？**

主要放在 `SKILL.md` 中。

包括：

- 核心目标
- 输入
- 任务解析
- 关键步骤
- 分支条件
- 异常处理
- 停止条件
- 输出
- 验证
- 资源导航

编排层不是长篇说明书，而应该像：

> **任务决策协议。**

---

## 7.3 知识层 Knowledge

解决：

> **完成任务时需要知道什么？**

通常放在：

```text
references/
```

包括：

- 领域规则
- Schema
- 政策
- 品牌规范
- 镜头语言
- 长文档
- 详细案例
- 模型差异
- 行业框架

原则：

> 只有相关分支发生时才读取。

避免把所有知识都塞进 `SKILL.md`。

---

## 7.4 执行层 Execution

解决：

> **哪些任务需要可靠执行，而不能只靠模型自由推理？**

通常包括：

```text
scripts/
assets/
tools/
MCP
external APIs
```

例如：

- 数据转换
- 文件校验
- JSON 校验
- 图像尺寸转换
- 视频信息抽取
- 批量处理
- 模板填充
- 文件生成

---

## 7.5 质量层 Quality

解决：

> **到底什么叫完成？怎么证明做对了？**

包括：

- Definition of Done
- Rubric
- 硬检查
- Eval
- Fixture
- 测试脚本
- 人工验收
- Regression Test
- Trace 检查

---

## 7.6 治理层 Governance

解决：

> **能力如何安全、可控地长期演进？**

包括：

- 版本
- 权限
- 数据边界
- 审计
- 变更记录
- 灰度发布
- 监控
- 回滚
- 最小权限原则

---

# 8. 推荐的 Skill 文件结构

```text
my-skill/
│
├── SKILL.md
│
├── agents/
│   └── openai.yaml
│
├── references/
│   ├── domain-rules.md
│   ├── output-schema.md
│   ├── examples.md
│   └── edge-cases.md
│
├── scripts/
│   ├── validate.py
│   ├── transform.py
│   └── check_output.py
│
├── assets/
│   ├── templates/
│   ├── examples/
│   └── project-skeleton/
│
└── evals/
    ├── dataset.jsonl
    ├── rubric.md
    ├── regression.jsonl
    └── fixtures/
```

# 9. 每类资源应该放什么

| 位置 | 应该放什么 | 什么时候读取 / 执行 | 不应该放什么 |
|---|---|---|---|
| `SKILL.md` | 核心工作流、决策点、边界、资源导航、验证 | Skill 触发后完整读取 | 长篇百科、所有变体细节、重复案例 |
| `references/` | 政策、Schema、框架、领域规则、详细案例 | 相关分支发生时按需读取 | 与正文重复的核心步骤 |
| `scripts/` | 计算、转换、抽取、校验、稳定命令 | 需要确定性结果时执行 | 只包一层简单工具、未经测试的脆弱脚本 |
| `assets/` | 模板、图片、字体引用、母版、项目骨架、示例 | 产物需要复用、填充、转换时 | 需要模型阅读理解的规则文档 |
| `agents/` | 界面元数据、可选依赖声明 | 宿主发现、展示、加载依赖时 | 核心业务流程唯一副本 |
| `evals/` | Prompt 集、Rubric、Fixture、基线、回归集 | 开发、发布前、持续监控 | 运行时必须依赖却未声明的隐式知识 |

# 10. Skill 必须做到“上下文经济”

一个 Skill 不是写得越长越专业。

如果 `SKILL.md` 有几万 Token，并且包含大量重复案例、长知识和所有特殊情况，它通常会带来：

- Token 浪费
- 核心规则被稀释
- 模型注意力分散
- 规则冲突增加
- 更新困难
- 测试困难

推荐原则：

> **核心流程留在 SKILL.md，长知识放 references，确定性执行放 scripts，复用素材放 assets。**

换句话说：

```text
必须每次知道的 → SKILL.md

有条件才需要知道的 → references/

需要精确执行的 → scripts/

需要直接复用的 → assets/

需要测试验证的 → evals/
```

---

# 11. SKILL.md 应该写什么

推荐结构：

```md
---
name: skill-name
description: 一句话说明该 Skill 在什么场景下解决什么任务
---

# Skill Name

## 1. Goal
明确 Skill 的核心目标。

## 2. Job Story
说明谁、在什么场景、为了什么目标使用该 Skill。

## 3. When to Use
定义应该触发的场景。

## 4. When Not to Use
定义不应该触发的场景。

## 5. Inputs
定义输入字段、必填项、可选项和默认策略。

## 6. Priority
定义冲突时的优先级。

## 7. Workflow
定义主要执行流程。

## 8. Decision Rules
定义关键判断逻辑与分支。

## 9. Failure Handling
定义异常、缺失和失败处理。

## 10. Resources
定义什么时候读取 references、什么时候调用 scripts。

## 11. Output
定义最终输出结构。

## 12. Definition of Done
定义任务完成标准。

## 13. Final Validation
定义交付前检查。
```

---

# 12. 不要把 SKILL.md 写成百科全书

以下内容不应该大量堆进 `SKILL.md`：

- 所有镜头语言知识
- 几十个完整案例
- 所有模型的参数
- 全部边界条件说明
- 重复的格式样例
- 大量行业背景知识
- 大段解释为什么这样做

因为 `SKILL.md` 的作用不是：

> 教模型完整学习一门课程。

而是：

> **告诉模型当前任务应该如何决策和执行，以及什么时候去读取更多知识。**

---

# 13. Skill 必须区分不变量与变量

这是高质量 Skill 非常重要的设计方法。

## 13.1 不变量

应该固化在 Skill 中。

例如：

- 必须步骤
- 质量门槛
- 安全规则
- 输出 Schema
- 必读规则
- 业务边界
- 停止条件
- 验证条件

---

## 13.2 变量

应该交给模型判断、参数、配置或外部输入。

例如：

- 用户背景
- 行业
- 风格
- 输出尺寸
- 语言
- 镜头策略
- 当前模型
- 场景
- 参考图片
- 业务主题

原则：

> **Skill 固化不变量，把变量留给模型判断或配置。**

这样 Skill 才具有泛化能力。

---

# 14. 把正文写成“决策协议”，而不是解释性文章

一个高质量 Skill 的正文应该尽量减少：

```text
为了让结果更加专业……
在很多情况下我们建议……
这样做能够更好地……
```

应该更多写成：

```text
如果 A：
执行 B。

如果 B 失败：
执行 C。

如果缺少 X：
判断是否能够从上下文推断。

如果不可可靠推断：
请求澄清。

只有当 Y 满足时：
进入下一阶段。
```

也就是说：

> **减少解释性长文，增加可执行条件。**

---

# 15. Skill 必须有优先级系统

规则多了以后，一定会冲突。

推荐统一定义：

```text
P0 用户明确约束
↓
P1 安全 / 权限 / 数据边界
↓
P2 核心任务目标
↓
P3 业务规则
↓
P4 一致性 / 正确性
↓
P5 输出 Schema
↓
P6 质量增强
↓
P7 创意增强
```

冲突时：

> **高优先级覆盖低优先级。**

例如：

Skill 默认规则：

```text
动作高潮优先采用环绕运镜。
```

用户明确要求：

```text
摄像机固定，不允许运镜。
```

则必须服从用户明确要求。

---

# 16. Hard Constraints 与 Soft Guidelines 必须分开

这是避免模型“为了优化而违反底线”的关键。

---

## 16.1 Hard Constraints

违反即失败。

典型词：

- MUST
- MUST NOT
- REQUIRED
- NEVER
- ONLY IF

例如：

```text
- 九宫格必须是 3×3。
- 用户明确要求无文字时，不允许出现字幕、编号、水印和 Logo。
- 人物参考被锁定时，不允许无剧情依据修改发型和服装。
```

---

## 16.2 Soft Guidelines

用于优化质量，但不能覆盖硬约束。

典型词：

- SHOULD
- PREFER
- AVOID
- WHEN POSSIBLE

例如：

```text
- 优先避免连续三个相同景别。
- 情绪高潮优先使用更高视觉权重构图。
- 在不影响连续性的前提下增加景别变化。
```

---

# 17. Skill 必须包含异常处理

普通 Skill 只写：

```text
输入 → 执行 → 输出
```

成熟 Skill 应该覆盖：

```text
输入完整
→ 正常执行

输入有少量缺失
→ 使用默认策略

缺少重要信息但可以可靠推断
→ 基于上下文推断

存在多个合理解释
→ 选择风险最低方案

缺少决定性信息
→ 请求澄清

用户要求冲突
→ 按优先级处理

违反硬约束
→ 停止相关步骤或拒绝继续

脚本失败
→ 重试 / 降级 / 返回失败状态

外部工具失败
→ 判断是否存在安全替代方案

输出验证失败
→ 修复后重新验证
```

因此，一个成熟 Skill 必须同时包含：

> **Happy Path + Failure Path**

---

# 18. 一个关键节点至少回答五个问题

建议每一个关键 Workflow 节点都尽量回答：

```text
1. 需要什么输入？
2. 如何判断？
3. 下一步是什么？
4. 失败怎么办？
5. 什么时候停止？
```

例如：

```md
## 场景连续性检查

### 输入

- 上一镜头场景
- 当前镜头场景
- 剧情是否存在时间或空间跳转

### 判断

如果剧情没有明确空间切换：
当前镜头应延续上一镜头的空间关系。

### 检查

- 主体位置是否合理
- 出入口方向是否一致
- 背景核心元素是否延续
- 光照时间是否合理
- 道具是否无故消失

### 失败

发现无剧情依据的空间漂移时：
恢复上一镜头空间锚点，并重写当前镜头。

### 停止

空间逻辑与剧情均成立后进入下一步。
```

---

# 19. 好的 Skill 必须有 Definition of Done

以下词语不能直接作为完成标准：

- 专业
- 高级
- 完整
- 好看
- 有电影感
- 连贯
- 高质量
- 有创意

因为这些无法稳定检查。

应该将其转化为：

- 字段
- 状态
- 条件
- 指标
- Rubric
- 验收动作

---

# 20. 把抽象目标翻译成可检查条件

例如：

## 20.1 “人物保持一致”

不写：

```text
人物需要保持一致。
```

改成：

```text
若剧情没有明确要求人物外观发生变化：

- 年龄感保持一致
- 发型保持一致
- 发色保持一致
- 面部核心特征保持一致
- 主体服装保持一致
- 身材比例保持一致
- 关键配饰保持一致
```

---

## 20.2 “镜头丰富”

不写：

```text
镜头要丰富。
```

改成：

```text
- 不连续出现 3 个完全相同景别
- 至少存在一个建立空间关系的镜头
- 情绪高潮拥有对应近景或特写
- 景别变化必须服务于剧情，不允许为了变化而变化
```

---

## 20.3 “动作连贯”

不写：

```text
动作要自然连贯。
```

改成：

```text
相邻镜头：

- 主体位置具有逻辑连续性
- 动作状态能够自然衔接
- 运动方向不得无剧情依据突然翻转
- 核心道具不得突然消失
- 场景不得无剧情依据改变
- 人物姿态变化必须符合动作过程
```

核心原则：

> **把审美判断翻译成可检查条件。**

---

# 21. Definition of Done 示例

例如九宫格分镜 Skill，可以定义：

```md
## Definition of Done

只有同时满足以下条件，任务才算完成：

### 结构

- 输出包含 9 个有效画面
- 画面可以组成 3×3 Storyboard
- 每个画面承担明确剧情功能

### 剧情

- 九个画面共同构成连续事件
- 不遗漏核心剧情节点
- 不添加改变原故事逻辑的关键事件

### 人物

- 人物核心身份保持稳定
- 无无依据换装
- 无无依据年龄变化
- 无面部身份漂移

### 空间

- 场景关系稳定
- 无无依据瞬移
- 运动方向合理
- 重要道具连续

### 镜头

- 景别具有合理变化
- 关键情绪和动作拥有对应镜头权重
- 镜头变化服务叙事

### 可生成性

- 描述可以被图像模型直接理解
- 不依赖抽象概念表达画面
- 单帧不塞入过多连续动作

### 输出

- 格式符合指定 Schema
- 不包含用户禁止元素
- 无额外解释
```

---

# 22. 高质量 Skill 必须有 Rubric

Definition of Done 更像：

> **及格线。**

Rubric 用于：

> **区分 60 分、80 分和 95 分。**

例如：

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 剧情完整性 | 核心剧情缺失 | 基本完整 | 完整且重点突出 |
| 人物一致性 | 多次身份漂移 | 少量轻微漂移 | 全程稳定 |
| 空间连续性 | 明显跳跃 | 基本合理 | 连续且空间关系清晰 |
| 动作衔接 | 多处断裂 | 大部分可衔接 | 动作流畅自然 |
| 镜头设计 | 单一重复 | 有基础变化 | 镜头语言服务叙事 |
| 可生成性 | 抽象、难理解 | 基本可执行 | 高密度且直接可生成 |

---

# 23. Skill 必须能被 Eval

如果一个 Skill 没有 Eval，很难知道：

> 到底是能力稳定，还是偶尔碰巧生成得好。

因此可以认为：

> **没有 Eval 的 Skill，更接近 Prompt Prototype，而不是成熟能力。**

---

# 24. Eval 评的不是一句答案，而是一条执行链路

一次 Skill 运行可以抽象为：

```text
Prompt / User Input
↓
Routing
↓
Input Parsing
↓
Planning
↓
Decision
↓
Tool / Script
↓
Validation
↓
Artifact
↓
Final Output
```

同一个“最终结果不好”，可能来自完全不同的问题：

```text
A. Skill 没有触发
B. 触发了错误 Skill
C. 输入解析错误
D. 缺失信息没有澄清
E. 选择了错误策略
F. 步骤顺序错误
G. 工具选择错误
H. 参数错误
I. 漏掉验证
J. 输出 Schema 错误
K. Token 或 Tool Call 成本过高
```

所以 Eval 的第一价值不是打分，而是：

> **失败归因。**

只有失败可以被归因，才能知道应该改：

- description
- routing
- workflow
- references
- script
- tool
- rubric
- output schema

中的哪一层。

---

# 25. Skill Eval 推荐评测维度

| 维度 | 关键问题 | 示例指标 |
|---|---|---|
| Routing | 该触发时是否触发？不该触发时是否克制？ | Precision、Recall、误触发率、漏触发率 |
| Input | 缺信息时是否正确处理？ | 澄清准确率、无效追问率、升级正确率 |
| Process / Trace | 是否遵循关键步骤和顺序？ | 必做步骤覆盖率、工具选择正确率、权限升级次数 |
| Result / Artifact | 最终产物是否正确、完整、可用？ | 硬检查通过率、Rubric 得分、人工偏好率 |
| Robustness | 噪声、边界、环境变化下是否稳定？ | Pass@k、跨环境成功率、安全违规率 |
| Efficiency | 是否用合理成本完成任务？ | 时延、Token、工具调用数、无效循环率、人工接管率 |

---

# 26. Eval 集怎么构造

一个有价值的 Eval 集不应该只包含“写得很标准”的用户请求。

应该覆盖真实任务分布：

### 正例

明确应该触发 Skill 的请求。

### 相邻负例

看起来相似，但不应该触发 Skill 的请求。

### 边界例

需要进一步判断的模糊请求。

### 信息缺失例

缺少关键输入。

### 多目标例

用户一次提出多个任务。

### 噪声例

口语、错别字、冗余信息、上下文干扰。

### 冲突例

用户要求之间存在矛盾。

### 失败例

真实线上失败案例。

### Holdout

开发过程中不直接使用，用于防止过拟合。

# 28. 从最小版本开始 Eval

不建议一开始建立几百条复杂测试。

可以先从：

```text
10–20 条代表性样例
```

开始。

覆盖：

- 核心正例
- 相邻负例
- 边界例
- 缺失信息
- 真实失败

然后：

```text
发现失败
↓
归因
↓
加入 Regression Set
↓
最小修改
↓
重新评测
```

# 29. Skill 的开发应该采用最小有效修改

错误做法：

```text
发现一个失败
↓
重写整个 Skill
```

这样容易：

- 修好一个问题
- 又破坏三个旧能力
- 无法知道哪项修改真正有效

推荐：

```text
失败
↓
定位根因
↓
找到对应层
↓
进行最小有效修改
↓
运行目标测试
↓
运行回归测试
```

---

# 30. Skill 自进化的本质：质量飞轮

Skill 的自进化不是：

> “让模型自己改 Prompt。”

真正的自进化是：

> **真实失败不断被结构化为测试数据，并推动版本化能力改进。**

推荐飞轮：

```text
1. 观察
   ↓
真实目标 / 反馈 / 失败

2. 诊断
   ↓
聚类 + 根因定位

3. 提案
   ↓
最小变更候选

4. 沙盒评测
   ↓
目标集 + 回归集

5. 门禁批准
   ↓
阈值 / 人审 / 权限

6. 发布监控
   ↓
灰度 / 漂移 / 回滚

   ↺ 回到观察
```

---

# 31. 为什么必须版本化

如果 Skill 每次在线直接修改：

- 无法解释为什么结果变了
- 无法回归旧能力
- 无法做灰度实验
- 无法安全回滚
- 无法判断哪个版本真正更好

因此应该至少维护：

```text
Skill v0.1
Skill v0.2
Skill v0.3
Skill v1.0
```

每个版本最好记录：

```text
- changed
- reason
- related_eval
- expected_gain
- regression_result
- release_status
```

# 33. Skill Quality 公式

可以将高质量 Skill 简化为：

> **正确任务 × 正确触发 × 正确决策 × 稳定执行 × 明确验证 × 低成本运行 × 可控迭代**

进一步写成：

```text
Skill Quality
=
Routing
×
Reasoning
×
Execution
×
Evaluation
×
Governance
```

这里使用乘法，而不是加法。

原因是：

如果：

```text
Routing = 0
```

即使：

```text
Execution = 100
Evaluation = 100
```

最终 Skill 仍然无法正确解决用户任务。

同理：

如果：

```text
Evaluation = 0
```

即使输出偶尔很好，也无法可靠判断：

> 下一版到底有没有变好。

# 34. Skill 与 Prompt 的区别

| Prompt | Skill |
|---|---|
| 一段指令 | 一个能力单元 |
| 关注一次输出 | 关注长期稳定完成任务 |
| 主要描述怎么回答 | 定义何时触发、如何判断、如何执行 |
| 知识通常全部写在上下文 | 按需加载知识资源 |
| 主要依赖自然语言 | 自然语言 + Script + Tool + Asset |
| 结果经常主观判断 | 有 DoD、Rubric、Eval |
| 修改通常直接覆盖 | 版本化、回归、灰度、回滚 |
| 偶发成功即可接受 | 追求跨输入稳定成功 |

因此：

> **Prompt Engineering 解决的是“这次怎么让模型回答得更好”。**

而：

> **Skill Engineering 解决的是“如何把一次成功的方法沉淀成长期稳定能力”。**

# 35. Skill 的成熟度可以分为 5 个阶段

## Level 1：Prompt

特点：

- 一段角色和指令
- 没有路由
- 没有验证
- 没有 Eval

---

## Level 2：Workflow Prompt

特点：

- 有步骤
- 有输入输出
- 有基础约束

但：

- 缺少异常处理
- 缺少资源分层
- 缺少量化验证

---

## Level 3：Structured Skill

特点：

- 有 Job Story
- 有 Routing
- 有 Decision Protocol
- 有 Workflow
- 有 Hard / Soft Rules
- 有 DoD

---

## Level 4：Evaluated Skill

特点：

- 有 Eval
- 有 Rubric
- 有 Trace
- 有 Regression
- 有失败归因

---

## Level 5：Versioned Skill System

特点：

- 版本化
- 灰度
- 监控
- 回滚
- 真实失败自动进入候选测试集
- 持续数据驱动优化

最终目标应该是：

> **从 Prompt → Workflow → Skill → Evaluated Skill → Versioned Skill System**

# 36. 高质量 Skill 六层模型

```text
                      高质量 Skill
                           │
          ┌────────────────┼────────────────┐
          │                │                │
       1 发现层          2 编排层          3 知识层
      Discovery       Orchestration      Knowledge
          │                │                │
     什么时候触发       应该如何完成       需要知道什么

                           ↓

          ┌────────────────┼────────────────┐
          │                │                │
       4 执行层          5 质量层          6 治理层
      Execution          Quality         Governance
          │                │                │
     如何稳定执行       如何证明完成       如何安全演进
```

对应一句话：

> **发现层决定“该不该用”，编排层决定“怎么做”，知识层决定“知道什么”，执行层决定“能不能稳定做”，质量层决定“到底做没做好”，治理层决定“能不能长期放心地用”。**

# 37. 一个高质量 Skill 的最终检查清单

## 37.1 目标

- [ ] 是否只有一个核心 Job Story？
- [ ] 是否明确谁在什么场景使用？
- [ ] 是否明确最终结果？
- [ ] 是否定义成功标准？

## 37.2 Routing

- [ ] 是否定义 Positive Cases？
- [ ] 是否定义 Negative Cases？
- [ ] 是否定义 Boundary Cases？
- [ ] 是否考虑误触发？
- [ ] 是否考虑漏触发？

## 37.3 Input

- [ ] 是否定义必要输入？
- [ ] 是否定义可选输入？
- [ ] 是否定义默认值？
- [ ] 缺失信息时是否知道什么时候推断？
- [ ] 是否知道什么时候必须追问？

## 37.4 Decision

- [ ] 是否存在关键判断节点？
- [ ] 每个判断节点是否有条件？
- [ ] 是否知道不同条件对应什么策略？
- [ ] 是否定义冲突优先级？

## 37.5 Workflow

- [ ] 是否有明确执行顺序？
- [ ] 是否存在 Happy Path？
- [ ] 是否存在 Failure Path？
- [ ] 是否定义停止条件？
- [ ] 是否避免无效循环？

## 37.6 Freedom

- [ ] 创意任务是否给模型足够自由度？
- [ ] 确定性任务是否交给脚本或工具？
- [ ] 是否避免所有步骤都由模型自由发挥？
- [ ] 是否避免所有细节全部写死？

## 37.7 Resources

- [ ] SKILL.md 是否只保留核心流程？
- [ ] references 是否按需加载？
- [ ] scripts 是否承担确定性操作？
- [ ] assets 是否只存复用资产？
- [ ] 是否存在重复内容？

## 37.8 Constraints

- [ ] Hard Constraints 是否明确？
- [ ] Soft Guidelines 是否明确？
- [ ] 是否存在优先级？
- [ ] 是否定义不能做什么？

## 37.9 Output

- [ ] 输出 Schema 是否明确？
- [ ] 是否能够直接交给下游使用？
- [ ] 是否避免不必要解释？
- [ ] 是否有格式验证？

## 37.10 Quality

- [ ] 是否有 Definition of Done？
- [ ] 是否有 Rubric？
- [ ] 是否有硬检查？
- [ ] 是否可以客观判断“完成”？

## 37.11 Eval

- [ ] 是否有正例？
- [ ] 是否有负例？
- [ ] 是否有边界例？
- [ ] 是否有真实失败？
- [ ] 是否有 Regression Set？
- [ ] 是否可以做失败归因？

## 37.12 Governance

- [ ] 是否版本化？
- [ ] 是否有变更记录？
- [ ] 是否有权限边界？
- [ ] 是否支持灰度？
- [ ] 是否支持回滚？
- [ ] 是否监控线上漂移？

# 38. 最终定义

可以将“什么是好的 Skill”最终定义为：

> **高质量 Skill 是围绕单一、明确 Job Story 构建的版本化能力单元。它能够被准确发现和触发，根据输入与上下文自主选择正确策略，将开放式判断、领域知识与确定性执行合理分层，并通过完整的异常处理、Definition of Done、Rubric 与 Eval 对执行链路进行验证。同时具备最小权限、资源按需加载、可追踪、可回归、可灰度与可回滚能力，使一次性的 Prompt 能力真正沉淀为稳定、可复用、可持续优化的系统能力。**

---

# 39. 一句话总结

> **好的 Skill，不是告诉模型“怎么回答”，而是定义一个任务什么时候该做、应该怎么判断、如何稳定完成、怎样才算完成，以及失败后如何持续变好。**

---

# 40. 最简版方法论

如果只保留一套最核心的方法，可以记住：

```text
先定义任务
↓
再定义触发
↓
再定义决策
↓
再定义执行
↓
再定义完成
↓
再建立 Eval
↓
最后做版本化迭代
```

最终目标不是：

> 写出一份更长的 Prompt。

而是：

> **把人的专业经验，沉淀成可以被机器稳定调用、可靠执行、持续进化的能力资产。**
